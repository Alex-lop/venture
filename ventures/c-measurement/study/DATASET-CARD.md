# Dataset card — Track M differential verifier, 2026-08-31

Two CSVs, both tracked: **`results-prs.csv`** (107 rows, one per attempted pull request) and
**`results-tests.csv`** (13,564 rows, one per PR-touched test id). A third tracked CSV,
**`../corpus/funnel-v2.csv`** (1,908 rows, one per repo the corpus search surfaced), carries the
funnel — see Provenance step 1. They are the complete
output of `runner.py` over the 107 sample PRs of the 25 buildable repositories; the method
that produced them is `METHOD.md`, the analysis is `WRITEUP.md`, and every number in either
is regenerated by `python3 analysis.py`, whose `== RED-TEAM PASS (2026-08-31) ==` block
prints every figure added or corrected in the 2026-08-31 revision.

Row counts here are verifiable with
`wc -l results-prs.csv results-tests.csv` (108 and 13,565 including headers).

## `results-prs.csv` — one row per attempted PR

| column | type | meaning |
|---|---|---|
| `repo` | `owner/name` | the repository. Join key with `results-tests.csv`, with `../pilot/results.csv` and with `../corpus/candidates-v2.csv`. |
| `pr` | int | PR number. `(repo, pr)` is the primary key and the runner's resume key: a pair already present is never re-run. |
| `base_sha` | 40-hex | `pulls/N.base.sha` — the counterfactual the tests were run on. **Not** necessarily `merge_sha^1`; see `base_is_merge_first_parent`. |
| `merge_sha` | 40-hex | `pulls/N.merge_commit_sha` — the candidate side. |
| `merged_at` | ISO-8601 Z | when the PR landed. Range in this file: 2026-06-12 .. 2026-08-31. |
| `n_tests` | int | rows this PR contributes to `results-tests.csv`. 0 when the run never produced a report. |
| `n_f2p` | int | `FAIL_TO_PASS` rows for this PR. |
| `n_p2p` | int | `PASS_TO_PASS` rows. |
| `n_unresolved` | int | `UNRESOLVED` rows. |
| `pr_verdict` | `DISCRIMINATING` \| `NON_DISCRIMINATING` \| `UNRESOLVED` | `DISCRIMINATING` iff `n_f2p >= 1`; `NON_DISCRIMINATING` iff `n_p2p >= 1 AND n_f2p == 0 AND n_unresolved == 0`; otherwise `UNRESOLVED`. |
| `unresolved_reason` | enum, else empty | why no verdict. Values in this file: `install_failed_base` (3), `base_run: timeout` (2), `no runnable test file (test paths were conftest/fixtures only)` (1), `base_run: junit xml unparseable` (1), `partial evidence: 16 unresolved rows` (1). `METHOD.md` §"The verdict table" lists the full vocabulary the runner can emit. |
| `cc_type` | token, else empty | leading conventional-commit type of the PR title (`fix`, `feat`, `refactor`, `docs`, `test`, `chore`, `perf`, `build`, `ci`, `style`, `revert`). **Only the type token is extracted; the title itself is never stored.** Distribution here: `fix` 45, `(none)` 31, `feat` 26, `perf` 2, `chore` 1, `ci` 1, `refactor` 1. |
| `pr_trailer_kinds` | `;`-joined keys | which of the corpus's ten agent trailers appear **in this PR** (body, falling back to its commit messages), matched with `corpus/scripts/widen.py`'s verbatim regexes. **Only the keys are stored, never the matched text.** Distribution: `claude-code-gen;robot-gen` 92, `claude-coauthor` 11, `copilot` 4. |
| `base_is_merge_first_parent` | `1` \| `0` \| empty | `1` when `base_sha == merge_sha^1`, i.e. the base really is the target branch immediately before the PR landed. Empty when `merge_sha^1` could not be resolved. The sensitivity stratum in `WRITEUP.md` §Threats 6. |
| `unmatched_testish_files` | int | files a deliberately wider **auditor** path rule calls a test while the strict run-set rule does not. | `changed_lines` | int | `additions + deletions` from the PR payload. Median 357, min 22, max 1,846. The corpus admitted only PRs ≤ 2,000. |
| `test_files_new` | int | test-path files with status `added`. |
| `test_files_modified` | int | test-path files with status `modified` / `renamed`. |
| `infra_changed` | `1` \| `0` | the PR touched `conftest.py`, `pytest.ini`, `tox.ini`, `setup.cfg`, or a `fixtures/` directory. These travel *with* the test patch onto the base, so the base run's goalposts move — read such rows as lower-confidence. 5 of 107 rows. |
| `repo_trailer_kinds` | `;`-joined keys | **a repo-level attribute carried over from `candidates-v2.csv`**, not a claim about this PR. Never use it for a per-agent breakdown; use `pr_trailer_kinds`. |
| `duration_s` | float | wall-clock seconds for this PR's ten container steps. Sum 4.3 h, mean 145 s, max 4,576 s. |

## `results-tests.csv` — one row per PR-touched test id

| column | type | meaning |
|---|---|---|
| `repo`, `pr` | | join key to `results-prs.csv`. |
| `test_id` | `classname::name` | as emitted by pytest into the JUnit report, including any `@parametrize` id, with email-shaped substrings replaced by `<email>` (see §"What is deliberately absent"). A PR that renames a module, moves a test between classes or changes a parametrize id produces a different id and therefore a `missing` side (`METHOD.md` Known limits #6). |
| `pre_patch_outcome` | `passed` \| `failed` \| `error` \| `skipped` \| `absent` | how the id behaved on the **unpatched** base — the base-greenness covariate. `absent` means the id did not exist there, which is the added-test case. **This column never enters the verdict**; it is a filter the reader may apply, and it is the one that separates the tests the PR *wrote* from the tests it merely re-ran — see gotchas 2 and 4. Distribution: `passed` 12,165, `absent` 1,248, `skipped` 136, `failed` 15, `error` 0. |
| `base_outcome` | `passed` \| `failed` \| `error` \| `skipped` \| `missing` \| `flaky` | the id on the patched base, from two runs. `flaky` = the two runs disagreed. `error` includes "the id's module raised a collection failure", which is how a test for a not-yet-existing module reads. Distribution: `passed` 10,433, `error` 2,202, `failed` 785, `skipped` 140, `flaky` 3, `missing` 1. |
| `candidate_outcome` | same vocabulary | the id on the merge commit, from two runs. Distribution: `passed` 13,386, `skipped` 155, `failed` 23. |
| `verdict` | `FAIL_TO_PASS` \| `PASS_TO_PASS` \| `UNRESOLVED` | `FAIL_TO_PASS` iff base ∈ {`failed`, `error`} and candidate = `passed`; `PASS_TO_PASS` iff both `passed`; everything else `UNRESOLVED`, with the reason readable from the two outcome columns. Distribution: 10,432 / 2,948 / 184. |

**Six gotchas that change what an aggregate means.**

1. **A fatal run stamps `UNRESOLVED` on every row of that PR**, whatever the other side said.
   This is what makes `results-tests.csv` safe to aggregate *without* joining to
   `results-prs.csv`: no test-level total can count a run that never happened as evidence.
2. **`FAIL_TO_PASS` is not one thing, and `base_outcome` alone does not tell you which.**
   2,181 of 2,948 (74.0%) have `base_outcome=error` and 767 (26.0%) `base_outcome=failed`.
   **Crosstab `base_outcome` against `pre_patch_outcome` before interpreting either**
   (`python3 analysis.py`, `== RED-TEAM PASS ==` tag `[A2]`):

   | base | pre-patch | rows | share | mechanism |
   |---|---|---:|---:|---|
   | `error` | `passed` | 1,727 | 58.6% | a pre-existing **passing** test broken by an import the PR's own test patch added — collateral, not evidence about the change |
   | `failed` | `absent` | 635 | 21.5% | a newly-added test failing an assertion at base |
   | `error` | `absent` | 454 | 15.4% | the module-arrives-with-its-test shape |
   | `failed` | `passed` | 131 | 4.4% | a pre-existing test the patch edited into failing at base |
   | `failed` | `failed` | 1 | 0.0% | — |

   Reading the 74.0% as "the PR added the module too" is wrong for 58.6% of the rows.
   `WRITEUP.md` §Results 3 publishes this table and the per-PR re-score without the
   collateral rows (still 0/99).
3. **Only the PR's own test-path files were run**, never the repo's whole suite, so
   `PASS_TO_PASS` here is scoped to the tests the PR touched and is not SWE-bench's
   repo-wide regression set (`METHOD.md` Departures #1).
4. **A row is a parametrize-expanded test id, not a test function, and "PR-touched" is not
   "PR-written".** One `@parametrize`d function can contribute hundreds of rows — one module
   supplies 742 ids in a single PR — and **12,163 of 13,380 resolved ids (90.9%) are
   pre-existing tests being re-run**. For the PR's *own* tests, filter
   `pre_patch_outcome == "absent"`: 1,248 ids, 1,217 resolved, of which 128 (10.5%) are
   `PASS_TO_PASS` against 78.0% over all touched ids. That column is a **proxy** for
   "introduced by this PR" — a renamed module or a changed parametrize id also reads
   `absent` (`METHOD.md` Known limits #6) — so it over-counts new tests and 10.5% is an
   upper bound.
5. **Rows cluster hard.** 107 PRs sit in 25 repos; one repo supplies 4,954 of 13,564 ids
   (36.5%), and **the two largest module-level collection events supply 1,475 of 2,948 =
   50.0% of every `FAIL_TO_PASS` row** (`WRITEUP.md` §Results 3; both are the same module, in
   two PRs of that repo — those two PRs together supply 1,490 rows = 50.5%). Any
   interval computed as if rows were independent is much too narrow: the pooled Wilson
   interval on the 78.0% is [77.3%, 78.7%], a 25-repo cluster bootstrap is [71.0%, 87.2%].
   Aggregate by repo or PR, or bootstrap over repos.
6. **`results-prs.csv` has a row for every attempted PR; `results-tests.csv` does not.**
   6 of the 107 PRs produced zero test rows. Test rows per PR: 0 .. 1,919 (median 42) over
   all 107, or 1 .. 1,919 (median 43) over the 101 that produced any.

## What is deliberately absent

Nothing in either tracked CSV identifies a person.

- **No author, no login, no email, no display name** for any PR author, committer, reviewer or
  merger. Raw GitHub payloads do carry logins; they stay in `raw/`, which is gitignored
  (`.gitignore:15`), as are the per-phase container logs in `logs/` (`.gitignore:14`).
- **No PR title and no PR body.** Only two derived tokens survive: `cc_type` (the leading
  conventional-commit word) and `pr_trailer_kinds` (which trailer *keys* matched).
- **No source code, diff, patch or log text** from any studied repository.
- **No `merged_by` / `author` column**, so the self-merged vs independently-merged
  stratification `DECISION.md` v4's M-power row asks for cannot be computed from this dataset.
  That is a genuine gap in the result and is recorded as such in `WRITEUP.md` §Threats 9(i)
  ("Not computable from this dataset"), not quietly omitted.

**Email-shaped strings in `test_id` are masked.** `test_id` is copied verbatim from pytest,
and a `@parametrize` id can embed an email-shaped fixture (a repo testing a trailer detector
parametrizes over `Co-authored-by:` lines). `runner.py`'s `scrub_id` replaces anything matching
`[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` with the literal `<email>` before a row is
written, so nothing email-shaped reaches a tracked file. **9 of 13,564 ids carry `<email>`; 0
rows contain an `@`** (`grep -c '<email>' results-tests.csv`, `grep -c '@' results-tests.csv`).
The published run was launched minutes before `scrub_id` was added, so the mask was applied to
the finished file post-hoc using the same function imported from `runner.py` — which is exactly
what a re-run emits. It is a 1:1 substitution here: row count, unique `(repo, pr, test_id)`
count, and every number in `analysis.py`'s output are identical before and after.

Verification: `grep -ciE 'author|login|email|committer' results-prs.csv results-tests.csv`
returns 24 and 322 — and every one is benign. In `results-prs.csv` they are the trailer key
`claude-coauthor` (19) and the repository name `AvaCodeSolutions/django-email-learning` (5,
`grep -icE 'author|login|email|committer' results-prs.csv` minus
`grep -c 'claude-coauthor' results-prs.csv`). In `results-tests.csv` they are the 9 `<email>` masks plus test
class and function names from the studied repos' own suites — `TestAuthorValidator`,
`TestCoAuthorSkip`, `TestGitCommitterConfig`, `test_validate_author_in_ignored_list` —
enumerable with
`grep -ioE '[a-z_]*(author|login|email|committer)[a-z_]*' results-tests.csv | sort | uniq -c | sort -rn`.

## Reproducing the dataset

```sh
cd ventures/c-measurement/study
python3 runner.py --selfcheck    # parser + verdict asserts; no docker, no network
./run.sh                         # regenerate both CSVs; resumable, skips finished (repo, pr)
python3 analysis.py              # every number in WRITEUP.md and SUMMARY.md
```

Requires docker and a read-only `gh` login. ~4.3 h of container time at `--jobs 3` on
linux/arm64. Re-running is not bit-identical: `duration_s` varies, and a test whose base
behaviour is genuinely unstable can land in a different cell. Observed: **3 `flaky` rows,
all in one module, out of 27,128 side-observations**. That is a **floor on id-level
instability and bounds nothing else** — the two runs of a side are consecutive in one
container, and the 2,181 error-at-base rows come from only 87 module-level collection
events, so one unstable import would move up to 742 rows at once and be observed twice
identically. `WRITEUP.md` §Threats 5 states this; do not quote 3/27,128 as a bound.
